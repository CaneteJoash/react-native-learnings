# The same two-screen stack, three ways

Scope: `List → Detail(id)`, the core of FieldKit's Notes stack. Same behavior, three
implementations, diffed.

## 1. Expo Router (file-based) — what FieldKit actually uses

```
app/(tabs)/notes/index.tsx        // List
app/(tabs)/notes/[id]/index.tsx   // Detail
```

```tsx
// app/(tabs)/notes/index.tsx
<Link href={{ pathname: '/notes/[id]', params: { id: item.id } }} asChild>
  <Pressable><ThemedText>{item.title}</ThemedText></Pressable>
</Link>

// app/(tabs)/notes/[id]/index.tsx
const { id } = useLocalSearchParams<{ id: string }>();
```

No `Stack.Navigator`, no param-list type, no linking config to write by hand. The
folder structure *is* the route graph and the deep-link table; `[id]` becomes both
the URL segment and the typed param. Types come from a generated `.expo/types/router.d.ts`
(regenerated by the dev server / build), not hand-written — that's the one real cost:
you're trusting codegen instead of reading a type in the file.

## 2. React Navigation — static config (`@react-navigation/native` `createStaticNavigation`)

```tsx
const RootStack = createNativeStackNavigator({
  screens: {
    List: ListScreen,
    Detail: {
      screen: DetailScreen,
      linking: { path: 'notes/:id' },
    },
  },
});

type RootStackParamList = StaticParamList<typeof RootStack>;
declare global {
  namespace ReactNavigation { interface RootParamList extends RootStackParamList {} }
}

const Navigation = createStaticNavigation(RootStack);
// App: <Navigation />
```

```tsx
// DetailScreen
function DetailScreen({ route }: NativeStackScreenProps<RootStackParamList, 'Detail'>) {
  const { id } = route.params; // typed, no `any`
}
```

Object literal instead of JSX for the tree; params are inferred from the config object
via `StaticParamList`, so there's one source of truth and no separate `ParamList` type
to keep in sync by hand — closest in spirit to Expo Router, but the graph lives in a
JS object instead of the filesystem, and deep-link paths are declared per-screen
inline rather than derived.

## 3. React Navigation — dynamic config (classic JSX)

```tsx
export type RootStackParamList = {
  List: undefined;
  Detail: { id: string };
};
const Stack = createNativeStackNavigator<RootStackParamList>();

<Stack.Navigator>
  <Stack.Screen name="List" component={ListScreen} />
  <Stack.Screen name="Detail" component={DetailScreen} />
</Stack.Navigator>
```

```tsx
function DetailScreen({ route }: NativeStackScreenProps<RootStackParamList, 'Detail'>) {
  const { id } = route.params;
}

// separate linking config object, kept in sync by hand:
const linking = { config: { screens: { Detail: 'notes/:id' } } };
```

`RootStackParamList` is hand-written and is the only type contract — most explicit,
most boilerplate, and the one place a typo (`Detial: string`) silently breaks nothing
until runtime, since nothing generates or checks it against the actual screens declared
in JSX. Linking config is a fully separate object you must remember to update whenever
a screen or its params change.

## Diff, in one line each

| | Route graph lives in | Params come from | Deep-link path comes from | Boilerplate |
|---|---|---|---|---|
| Expo Router | filesystem | codegen (`useLocalSearchParams<T>()`) | filesystem, automatic | lowest |
| RN static | one config object | `StaticParamList<typeof tree>` | inline per screen in config | low |
| RN dynamic | JSX tree | hand-written `ParamList` type | separate `linking` object | highest |

Net: Expo Router trades an explicit, greppable param-list type for zero-maintenance
routing; RN dynamic trades convenience for a fully explicit, no-codegen contract; RN
static sits in between — one config object, one inferred type, but still not tied to
the filesystem.

## Stretch: why only `id` in `fieldkit://notes/:id`

The URL identifies a *resource*, not a *view of it*. `id` is the only value needed to
look the note up — everything else the Detail screen might want (title, scroll
position, which field is focused, where to navigate back to) is either re-derivable
from that id by reading the note, or is session/UI state that doesn't belong in a
link at all. Two concrete reasons to keep it that stops there:

- **Stability & shareability.** A link is a promise that survives longer than the
  session that created it — pasted in Slack, opened cold days later. Anything beyond
  the id (e.g. a cached title, an index into a list that's since changed) can go
  stale and point to the wrong thing. The id alone is guaranteed correct as long as
  the note exists.
- **Single source of truth.** If the URL carried denormalized fields, the app would
  have two disagreeing sources for the same data (the link's stale copy vs. the
  store's live copy) and would need reconciliation logic. Fetching by id and treating
  the id as the only input keeps Detail a pure function of `(id) → note`.
